# NexusOps Client 功能与界面重构方案

状态：设计建议与可交互线框，尚未替换客户端业务界面。依据当前 `f811e352` 源码和用户提供的 SkillOps 截图。默认方向为团队员工工作台优先，完整开发配置继续保留；产品定位问题已提出，后续按用户反馈调整。

预览：[可交互线框](./client-workbench-preview.html)。所有数字和活动均为明确标记的示例，页面不会修改工具配置、读本机对话或发送统计。

## 结论

借鉴参考图的固定侧栏、统一筛选、主次分区和可追踪状态。首页应帮助员工判断「现在能用什么、需要处理什么、下一步点哪里」。资产治理、成员排名、组织策略等管理任务继续留在 NexusOps 管理后台。

参考图的紫色只是视觉参考，不必把每个容器都做成紫色边框或发光背景。保留客户端浅色 / 深色主题和原生窗口操作，正文使用清晰的系统无衬线字体。默认以 1280×800 的桌面窗口设计，窄窗口收起辅助区，不能靠缩小字号塞入内容。

## 当前产品的具体问题

| 现状与源码 | 用户遇到的问题 | 建议 |
| --- | --- | --- |
| `src/App.tsx` 默认进入 providers，Team 在供应商页头部图标中 | 团队功能像附加插件，初次使用难以找到 | 稳定的文字侧栏；已连接组织的新用户进入工作台，已有用户保留上次页面 |

| `TeamPage.tsx` 同时承载连接、配置导入、资产同步、漂移恢复和统计，1348 行 | 一页多个任务，重要操作被长表单和技术信息挤走 | 按工具接入、资产库、组织与上报拆分；先移动组件，再调整交互 |
| `ToolUsagePanel` 位于已连接 Team 页最上方 | 隐私说明和采集开关长期占据主任务区域 | 首次连接时说明数据边界；常态只显示上报摘要，设置集中在「组织与上报」 |
| 团队资产与本地 Skills / Prompts / MCP 各自有入口 | 员工无法清楚区分来源、所有权和生效工具 | 一个资产库入口，区分「团队发布 / 个人本地」，按类型和目标工具筛选 |

## 参考图中不能直接照搬的内容

- 「运行结果率 0.0%」不能替代「无结果数据」。没有可靠成功 / 失败信号就显示「未采集」，不能暗示员工工作失败。
- 当前 Hook 仅包含 runtime、event、timestamp、id。它不包含 Skill ID、版本、duration、model、cost 或结果，不能支持参考图中的 Skill 排名、版本建议、执行时长与 Skill 成本。
- 已有本机用量模块包含请求、Token、估算费用等统计，但与组织网关账单、Hook 上报计数是不同数据源；不能混合相加或都命名为「使用量」。
- 右侧活动不能默认展示对话片段、项目路径和提示词。即使本机能读取会话，默认上传边界仍维持当前四字段白名单。
- 员工客户端不需要把 Skill Lab、Registry、Governance、Team 管理都平铺成一级菜单。研究评测和正式审批是后续独立范围。

## 新的信息架构

| 入口 | 默认内容 | 次级内容与操作 |
| --- | --- | --- |
| 工作台 | 当前组织、工具状态、待处理问题、团队资产摘要 | 打开工具接入、查看变更、恢复上报；不自动执行变更 |
| 工具接入 | Codex、Claude Code 等已启用工具及其实际能力 | 团队配置 / 个人配置、配置预览、导入、显式启用、连接检测、Hook 检测 |
| 资产库 | 当前授权 stable 团队资产与本地安装状态 | 团队 / 个人来源、Skill / Prompt / Rule 类型、目标工具、版本详情、变更预览、同步、冲突恢复 |
| 使用记录 | 本机模型请求与费用概览、明细 | 工具、时间、模型筛选；独立查看组织上报状态，保留数据源说明 |
| 组织与上报（次级） | 当前组织、成员身份、连接状态、采集状态 | 导入 Profile、重新认证、上报开关、待上传数量、最近上传、修复 Hook、退出组织 |
| 设置（次级） | 外观、语言、更新、启动和数据管理 | 日志、代理端口、备份、配置路径等高级项 |

现有 MCP、Agents、通用供应商、会话、OpenClaw / Hermes 配置均保留。第一阶段集中放入工具页的「高级配置」或资产库对应类型，提供直接入口，不通过删功能来获得整洁界面。

## 首页布局与操作优先级

1. 顶部只放页面名称、当前组织和一个主要动作。工作台主要动作为「配置工具」；资产页为「检查更新」，不能所有页面都复用「新增供应商」。
2. 紧凑状态栏：已连接组织、可用工具、上次同步。配置存在、检测通过、Hook 已确认必须分开命名。
3. 主区域首先是工具列表：工具、当前配置来源、连接状态、采集状态、明确动作。个人配置和团队配置不能混成一个无来源的「当前供应商」。
4. 右侧窄栏只展示有下一步动作的问题，例如凭据过期、2 项本地冲突、上报失败。没有问题时收起，不用空白排行榜填充。
5. 下方展示团队资产更新摘要。查看变更后才允许覆盖；有本地编辑时提供保留本地、查看差异、明确覆盖 / 恢复选择。
6. 窄窗口将待处理问题放到工具列表上方，数据表切换为字段清晰的列表；不隐藏错误和冲突。

## 三条关键流程

### 首次接入

连接组织 / 导入 Profile → 显示组织和本人身份 → 选择工具 → 预览将修改的配置 → 确认导入 → 明确启用 → 验证连接。

使用统计单独说明管理员能看到哪些数据，并提供明确开关。不应因为点击「连接组织」就自动覆盖个人配置、切换供应商或开启上报。

### 团队资产更新

检查 stable 清单 → 列出新增 / 更新 / 冲突 / 撤回 → 选择目标工具与资产 → 查看差异 → 同步 → 展示逐项结果与恢复入口。

组织撤权与本机文件状态分开显示。服务端撤回不意味着自动删除已经下载的文件，离线也不意味着本地文件丢失。

### 统计与故障恢复

使用记录查看本机调用 → 组织与上报查看采集开关、排队数量、最近成功时间 → 错误对应重新认证 / 修复 Hook / 重试上传。

「Hook 已安装」与「已观察到真实事件」分开显示；接管代理正在运行，也不意味着所有请求均被记录。未知状态不能显示绿色已连接。

## 数据可用性与开发边界

| 界面内容 | 已有能力 | 仍需补齐 |
| --- | --- | --- |
| 本机请求、Token、估算费用、趋势、工具分布 | `usageApi.getUsageSummary / getUsageSummaryByApp / getUsageTrends` | 调整入口，明确数据源和缺失值；不新增模型调用 |
| 组织和成员 Key 元信息、授权模型 | Team Profile / `getTeamStatus` | 常驻上下文摘要，过期和断连状态设计 |
| 团队资产版本、同步计划、漂移和恢复 | `previewTeamSync / syncTeam / getTeamLocalHistory` | 按任务拆页面，抽出复用组件；不改写安全边界 |
| 上报启用、待上传、累计上传、最近错误 | `team_tool_usage_status` | 展示更明确的错误与恢复路径 |
| 每工具的真实 Hook 确认状态 | 目前没有按工具的确认时间 | 新增本机最小状态聚合接口，不能拿配置文件存在代替 |
| 按日期显示员工自己的 Hook 运行历史 | 已确认事件从待上传队列删除 | 需单独的本机聚合保留策略 / 只读接口；不能读取待上传队列冒充完整历史 |
| 全工具统一连接健康状态 | 各工具能力、检测实现不同 | 统一状态契约及能力映射；保留「未检测 / 不支持」 |

第一阶段优先复用现有数据做界面重排；新增采集字段、服务端行为或本机历史存储必须单独定义契约、隐私边界和测试。

## 建议实施顺序和验收

### 第一阶段：入口和任务拆分

- 抽出 `ClientShell`、导航定义和页面标题动作；从设置中提供固定的使用记录入口。
- 拆分 Team 连接、供应商接入、同步清单和上报设置组件，保留原有 IPC 与处理逻辑。
- 兼容已保存的 `nexusops-client-last-view`，旧 view 有稳定映射；保留工具切换、窗口拖动、托盘和深链行为。
- 验收：新旧入口都可找到核心能力，统计入口不依赖代理开启，切页不会丢失待确认操作或自动触发导入 / 上报。

### 第二阶段：工作台与可恢复状态

- 用已有 API 做组织、工具及资产摘要，统一刷新、加载、无数据、断网、凭据失效与冲突状态。
- 整理工具配置预览和资产差异区，主要动作保持在可见区域。
- 验收：只改过配置显示「待验证」；同步失败保留成功项与重试入口；撤权不能误显示为删除成功。

### 第三阶段：本机观察记录

- 定义每工具最近事件与按日聚合的最小数据接口，明确保留期、清理、账号切换和采集禁用行为。
- 统一模型请求统计与 Hook 统计的文案与数据来源，保持其各自口径。
- 验收：重试不重复统计、不同组织隔离、不新增提示词或代码上传；不知道的值显示未知。

## 技术约束

保持 React / TypeScript / Tauri / Rust、现有 Radix 与 Tailwind 组件体系，不引入新的 UI 框架。页面拆分按用户任务边界，不为每块文字制造容器抽象。真正修改产品代码前，需要更新客户端 GitNexus 索引，对 `App`、Team 连接 / 同步和相关入口运行 impact，修改后核对 detect_changes；随后执行导航和交互回归、typecheck、构建与真实窗口检查。
