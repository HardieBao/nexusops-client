## 2. 总目标与完成定义

### 2.1 总目标

将当前以供应商配置为中心的客户端重构为团队工作台，实装 TeamAI 的受选资源适配和受控同步能力，让员工在一个客户端内完成：

**连接组织 → 配置 Codex / Claude Code → 获取授权团队资产 → 预览并同步 → 查看本人用量与上报状态 → 管理员查看对应员工的工具统计。**

员工使用交付包即可操作，不要求全局安装 TeamAI、Node.js 或通过终端完成配置。

### 2.2 首版必须满足的六个结果

| 结果 | 可判定的验收标准 |
| --- | --- |
| O1 功能找得到 | 四个主入口「工作台、工具接入、资产库、使用记录」持续可见；「组织与上报、设置」有固定次级入口；统计入口不依赖代理接管开关 |
| O2 原有能力可继续用 | T01 的旧功能迁移矩阵没有未映射项；个人供应商、MCP、Prompts、Skills、Agents、会话、原生窗口、托盘、深链等回归通过 |
| O3 TeamAI 真正接入 | 构建包含固定版本的 TeamAI 选定模块及许可；至少一组真实 TeamAI 格式的 Skill / Rule 经过模块处理、服务端批准发布，在两个首发工具中安装成功；只复制文案、加入依赖或嵌入网页不算完成 |
| O4 同步可信且可恢复 | 安装内容与授权 stable revision / 哈希一致；本地编辑不被静默覆盖；断网、撤权、取消、崩溃恢复和重复指令有明确结果 |
| O5 统计口径清楚 | 本机模型请求、组织网关费用、Hook 使用事件分开命名；一个事件只入账一次；管理员只能看当前授权范围；未知数据不显示为 0% 成功率 |
| O6 交付可直接试用 | Windows 包可启动并包含所需运行依赖；同版本服务端和控制台在 UAT 完成真实工具联调；有版本清单、检查结果、测试步骤和回退说明 |

**「全部完成」= T00—T23 全部通过 + M1—M5 全部通过 + 第 9 节硬性场景全部通过。**

只完成页面、代码提交或 ZIP 构建时，应分别报告「界面完成」「代码已提交」「已构建」，不能报告首版全部完成。后置扩展不计入首版完成条件。

## 3. 范围与不可破坏的约束

### 3.1 首版包含

- 客户端导航、应用外壳、首页，以及 Team 功能按任务拆页。
- 现有个人功能的入口迁移和兼容，不删除功能来简化界面。
- Codex / Claude Code 的工具接入、团队资产预览 / 同步、配置来源与状态展示。
- TeamAI 固定版本模块接入、Skill / Rule 资源适配、最小 HTTP 兼容及受控结果确认。
- 本机按工具的最近观察状态与最小日聚合，服务端仍使用当前工具统计口径。
- Windows x64 包、真实运行时 Hook、Gateway / 管理端 UAT 联调。

### 3.2 明确后置

| 扩展 | 本次处理 |
| --- | --- |
| TeamAI recall / learnings / teamwiki | 记录扩展位置，首版不实现知识库，不展示空的已上线入口 |
| 自动经验分享、Git 推送 / MR、会话摘要上传 | 不启用；以后单独定义内容预览、授权和保存策略 |
| 多 Git 来源自动拉取、每次会话自动升级资产 | 后置；首版不绕过 NexusOps 审批、stable 通道和本地冲突保护 |
| TeamAI 全量远程指令 | 不开放模型配置、插件安装、MCP 安装、Hook 修改和卸载客户端等远程动作 |
| 新增 Cursor、CodeBuddy、WorkBuddy 等首发支持 | 可保留已有个人功能；新融合能力标记未验收，不按上游 README 宣称已支持 |
| macOS / Linux 新集成实机验收、代码签名、公证、自动更新演练 | 后续发布里程碑；不阻断本次 Windows 核心试用，不宣称三平台正式发布 |
| Skill 执行成功率、工作效率排名、工作时长证明 | 不推断、不展示，没有可靠数据就不提供指标 |
| Platform 业务改造、新计费系统或数据库合并 | 不纳入 |

### 3.3 必须保持的约束

1. **单一文件写入者**：个人工具配置与团队资产由现有 NexusOps Rust 执行层写入；TeamAI 子进程只提供经过校验的资源描述 / 转换结果，不独立运行第二套安装器。
2. **单一身份来源**：组织 / 工作区 / 员工身份来自部署与认证上下文；主机名、本地路径、TeamAI 项目 ID 均不能授予权限。
3. **单一 Hook 管理入口**：保留已有无关 Hook，重复安装不重复注册，同一采集事件不能被两套 collector 各上传一次。
4. **凭据边界不扩大**：成员 Key 留在 OS 凭据存储；不进入 Node 参数、环境变量、日志、前端持久化或 TeamAI 的明文 token 文件。
5. **使用事件仍为四字段**：上报 `id / runtime / event / timestamp`。这限制的是使用遥测；必要的资产 revision、哈希、指令确认字段另按控制面协议审查，不能夹带设备清单、提示词或路径。
6. **不混合统计**：排队数量不是历史使用量；Hook 次数不是模型请求数；本地估算不是网关账单；完成一轮交互不等于任务成功。
7. **权限与恢复不降级**：只安装授权 stable 内容；保留版本校验、审批、撤权、漂移保护、明确覆盖和备份恢复。
8. **遵守仓库检查**：每次修改代码、测试、脚本、行为配置前检查 GitNexus 仓库 / 分支 / 索引；既有符号做 upstream impact，新增入口做 query / context；每轮修改及提交前做 detect_changes。失败时记录具体原因并用源码和聚焦测试补足。

| 决策 | 默认值与边界 |

| D02 项目 | 首版只绑定当前部署工作区，不新建独立项目系统；TeamAI 外部项目编号的映射、请求校验及稳定性在 T02 定义。不存在有效映射时拒绝，而非从 cwd 猜测 |
| D03 接入形式 | 固定 TeamAI 模块 + 结构化内部适配接口；不解析彩色 CLI 输出，不嵌入其完整 Dashboard。Node 能力如需要，随 Windows 包内置 |

| D06 自动行为 | 初次连接不自动覆盖配置、不自动切换供应商、不自动打开统计；会话开始不自动 Git pull / 执行安装 |
| D07 状态 | 配置存在、连接检测结果、Hook 注册状态、最近真实事件分别记录；检测和事件过期阈值在 T02 固定，不将历史成功永久显示为在线 |
| D08 本机统计 | 最近事件元信息与按日聚合独立于待上传队列；默认保留 30 天；按组织 / 工作区 / 本人成员身份隔离；界面提供清理 |
| D09 禁用语义 | 关闭采集：停止新增并清空待上传；已有本人本机聚合可保留至到期或主动清理。退出组织后其聚合不可在其他身份下显示，再次接入不自动启用采集 |
| D10 HTTP 范围 | 兼容层放在 Gateway 的版本化命名空间，通过类型映射复用已有能力；不把上游默认路由、双认证头或完整 report payload 原样暴露 |
| D11 UAT | 优先现有部署流程；托管 CI 不可用时可准备同 SHA 的本地检查和现有受控直接部署方案。不得绕过环境审批或伪造绿灯；实际部署未完成时 M5 仍未通过 |

## 7. 开发检查与提交规则

| 改动范围 | 至少执行的检查 |
| --- | --- |
| 客户端 React / TypeScript | 在客户端仓库执行 `pnpm typecheck`、`pnpm test:unit`、`pnpm build:renderer`；格式化变更文件并核对 diff |
| 客户端 Rust / IPC / 文件行为 | `cargo fmt --manifest-path src-tauri/Cargo.toml --check`；相关 Rust 测试；跨模块改动执行 `cargo test --manifest-path src-tauri/Cargo.toml --lib`；`cargo clippy --manifest-path src-tauri/Cargo.toml --lib -- -D warnings` |
| 客户端真实构建 | `pnpm tauri build --no-bundle` 作为构建检查；T21 另检查最终包含全部依赖的交付包。构建命令通过不代替包运行 |
| TeamAI 改编模块 | 对引入模块运行上游相关测试及自有适配合同测试；固定依赖版本，不默认运行完整 CLI 修改用户配置 |
| Gateway | 在 `apps/gateway-server` 执行 `go build -mod=readonly ./cmd/server`、相关包测试；共享认证 / 路由 / 合同改动执行 `go test ./...` 与 `go vet ./...` |
| Gateway Console | 主仓库执行 `pnpm --dir apps/gateway-console typecheck`、`lint:check`、`build` 及相关 Vitest；导航 / 权限整合需完整测试 |
| Schema / Wire | 按所属仓库生成指令更新，不手改生成文件；新增迁移同步 checksum、ledger，并实际测试升级与重复启动 |
| 部署脚本 / 工作流 | 按主项目 nexusops-verify 技能选择 shell、迁移合同与 Actionlint 检查 |
| 所有提交 | GitNexus 检查或明确的失败与替代证据；`git diff --check`；检查暂存 diff、未跟踪文件和敏感信息；仅提交本任务修改 |

工具链版本遵循各自仓库清单：当前客户端为 pnpm 10.12.3，主项目使用主项目清单，不为统一版本而改锁文件。Windows Rust 构建使用已验证的 MSVC 环境并记录版本。

测试中的环境依赖跳过必须逐项列出。跳过真实 Hook、真实包启动、UAT 或身份隔离硬性场景时，不能将对应里程碑标记通过。

## 8. 统一证据格式

每个任务至少记录：任务 ID、客户端 SHA、服务端 SHA、相关 TeamAI SHA、执行日期 / 环境、命令或操作步骤、期望值、实际值、通过 / 失败 / 阻塞、证据相对路径。

在 `acceptance.md` 中逐项使用以下记录格式；同一任务包含多个场景时分别记录，不用一个总的“测试通过”替代：

| 字段 | 必填内容 |
| --- | --- |
| 任务 / 场景 | 例如 T15 / S25 |
| 前置条件 | 工具版本、登录身份类别、已批准资产 revision、初始文件 / 队列状态；不填写真实密钥 |
| 操作 | 可重复执行的命令或编号步骤，包含故障如何注入和解除 |
| 期望结果 | 操作前写明文件、界面、服务端记录各应如何变化；引用对应场景标准 |
| 实际结果 | 实测数量、状态、哈希或错误；没有测量则写“未执行” |
| 环境与版本 | 本地夹具 / 本地真实服务 / UAT；源码 SHA，存在未提交修改时附 patch 哈希；包版本与哈希 |
| 结论与证据 | 未执行 / 通过 / 失败 / 阻塞，以及日志、截图或脱敏断言路径 |
| 剩余动作 | 失败或阻塞的具体原因、修复任务、重测条件；通过则填“无” |

任务只有在所属验收条件全部通过后才标记验收完成。代码已写但证据不足时保持“实施中 / 待验收”；依赖缺失时登记具体依赖，不删除场景或降低标准。

- 自动测试保留命令、退出码和通过 / 失败 / 跳过数。
- 文件行为保留脱敏后的路径类别、前后哈希、实际 revision 与恢复结果；不保存用户文件正文。
- HTTP 保留方法、接口模板、状态码和脱敏断言；不记录真实 Key、Cookie、token、原始请求内容。
- UI 保留对应版本截图、操作步骤和异常结果；合成数据截图必须明确标记。
- 发布保留包哈希、依赖版本、镜像 digest、迁移头、部署与回退结果。

## 10. 进度与最终报告口径

当前统计：T00—T23 共 24 项，T00—T02 共 3 项验收完成，T03—T04、T11—T15、T17 实施中。初始值为 0；计划文档本身不计入实施完成数。

每次汇报分别列出：

1. **代码状态**：哪些任务已实现、已提交、已推送。
2. **验证状态**：哪些里程碑 / 场景已实际通过，哪些失败或被跳过。
3. **部署状态**：UAT 实际版本、迁移、可访问入口；未部署就明确写未部署。
4. **交付状态**：Windows 包路径与哈希、真实工具验收结果、已知限制。

最终结论只能选择：

- **首版全部完成**：满足第 2.2 节完整定义。
- **部分完成**：列出已通过的任务 / 场景和剩余项，不使用模糊的「基本完成」。
- **外部条件阻塞**：明确任务 ID、具体错误、已完成的独立工作及解除条件；外部阻塞不改变其他未完成任务的事实。
